# Forge Nexxus

A mobile website builder backed by Convex. A member describes the site they want in the composer, Forge builds it as one self-contained page, and each follow-up prompt edits it. The build thread is where that conversation lives, the drawer lists their sites, and a site can be previewed and published to a public address. Everything runs on monthly credits: a plan grants an allowance per period, top-ups add more where the plan allows, and nothing rolls over. Users never see AI spend — only their credits — because the model is called server-side with the deployment's own key.

Live app: https://xgamer791.github.io/forge-nexxus/

`CLAUDE.md` holds the standing rules for working on this repository, the first being that all user data lives in Convex.

## Hosting

Standard GitHub Pages only, using the existing `.github/workflows/pages.yml` workflow and `docs/` output. Keep all asset paths relative to support `/forge-nexxus/`. `docs/forge-data.js` is a built artifact (see below) and is committed so Pages needs no build step.

## Local preview

Run `npm run dev`, then open http://localhost:4173/forge-nexxus/ . Any static server can also serve `docs/` directly. Rebuilding the data bundle or running the tests needs `npm install` first.

## What is in the app

- **Sign-in gate** (`docs/auth.js`): guests never reach the app. Building needs an account so credits belong to someone; a magic link, Google or Apple all create one.
- **Globe (top right)**: the active site's address, in a panel that comes down from the top — it belongs to the button that opened it, not to the thumb, so it keeps every sheet part and turns the geometry over: square at the top edge, rounded below, handle at the bottom. The name under the hosting domain is editable there, with the live link and whether it is published, and a custom domain is added, checked and removed in the same sheet on the plans that include them. Changing the address warns first, naming the address that stops answering. On a plan without `publicAddress` the globe opens the upsell instead of the picker — what an address and a custom domain come with, and the way through to the plan screen.
- **Drawer**: New site, the account's sites (most recently edited first, with rename and delete), a credits card showing the plan, what is left of this period and when it resets, and the account footer.
- **Settings**: Profile (name, linked sign-in methods, sign out, delete account), Appearance, Plan & credits (current plan and meter, plan cards with monthly and yearly prices, top-up packs where the plan allows them, Manage billing, downgrade at period end), Usage (the credit ledger), and Domains (custom hostnames pointed at a site, Premium only).
- **Composer**: the first prompt creates a site named after it and builds the first version; later prompts edit it. The reply appears in the thread as "Building your site…" until the build lands, and as a failure (with the reason) if it does not. A guest who somehow reaches it is sent to sign in.
- **Site bar and preview**: the bar above the composer names the active site and its state; Preview opens the latest build in a sandboxed frame (no scripts, no access to the app's origin) with Publish, Unpublish, the public address, and Download code on plans that include it. Sites on a plan without `removeBadge` carry a small "Built with Forge" badge, added as the page is served rather than stored, so upgrading takes it off every build at once. Publish is disabled on a plan without `publicAddress`, and says why, because there is nowhere to publish to.

## Both surfaces

`docs/` is one app: the same page serves the phone and the desktop website, so
a feature is never on one and missing from the other. Width is what differs.
`--shell` is the content column — 640px, 860px from 900px up — and the
composer, sheets, drawer and overlays are all positioned from it. The desktop
layer is a single `@media(min-width:900px)` block at the end of
`docs/styles.css`: the column widens, bottom sheets become centred dialogs, the
domain panel becomes a card under the globe, the drawer docks to the window as
a sidebar, and the preview opens at a website's width. `@media(hover:hover)`
adds the pointer affordances. Both widths get checked before a change is done;
`CLAUDE.md` holds that as a standing rule.

## Convex

- `convex/` holds the schema, Convex Auth setup (`auth.ts`), and the site, conversation, message, domain, billing, user, and settings functions. `npx convex dev` pushes them to the deployment named in `.env.local` (`CONVEX_DEPLOYMENT` plus `CONVEX_DEPLOY_KEY`, never committed) and regenerates `convex/_generated/`.
- `sites` is what a user builds. Each site owns a conversation (its build thread); `sites.create` makes both, `sites.remove` deletes the thread, its messages and the site's domains, and `messages.send` bumps the site's `updatedAt` so the drawer orders by last edit. Only members create sites, and a plan caps how many an account holds.
- `domains` are hostnames pointed at a site, added the way Wegic asks for them: one record. `domains.add` normalises a pasted URL to its host, refuses duplicates, anything already held by another account and anything under the hosting domain, and needs a plan with `customDomains`. `domains.list` carries the record to add — a `CNAME` for a subdomain, the registrar's root `ALIAS` for a bare domain — pointing at the site's own address. `domains.verify` is one button: the server resolves the hostname over DNS-over-HTTPS and writes back `active`, or stays `pending` with what it actually saw, so a browser can never mark its own domain verified. A domain that already resolves here is served while verification catches up.
- `subscriptions` is one row per member: the plan, the period, `credits` left this period, `reserved` by requests still running, and `granted` (the period's allowance plus its top-ups, which is the meter's full mark). Periods are one calendar month; when one ends the leftover expires, a scheduled downgrade lands, and the new allowance is granted. `creditLedger` records every movement and `creditHolds` tracks in-flight requests.
- `generate.run` answers a prompt. It records the prompt and a pending reply, holds the credits for the request (`generate` for a first build, `edit` after), sends the system prompt, the current page and the recent thread to any OpenAI-compatible chat completions endpoint, and stores the returned page as a `siteVersions` row before settling the hold. The model chooses between two replies: a build, which is one sentence and the complete page in an `html` fence, or an answer in plain prose when the user asked a question rather than for a change. An answer stores no version, leaves the current page alone, and settles the build hold at the `chat` rate, so asking what would suit the site costs a credit rather than a rebuild. A reply that starts a page and does not finish one is a failure, not an answer. A balance too thin for a build does not refuse the message: the turn becomes talk-only, held at the chat rate, with the model told it may not build and what standing in the way costs, so a free member can plan a site before paying for one. A page returned on such a turn is dropped rather than handed over for a credit. A failed call marks the reply `failed` with a scrubbed reason and releases the hold, so a build that produced nothing costs nothing. The endpoint, key and model come from `AI_BASE_URL`, `AI_API_KEY` and `AI_MODEL`; until they are set the build is refused with "Site generation isn't set up on this deployment yet".
- Addresses: every site answers on `<slug>.sites.forgenexxus.com`. The slug is the member's to pick — `sites.setSlug` takes it (letters, numbers and hyphens, 3–40 characters, reserved labels refused) and holds it for that site, published or not, while `sites.slugAvailable` answers the field as it is typed. `sites.publish` still assigns one from the name for anyone who never chose, and keeps it through unpublishing so links keep working. `SITES_DOMAIN` names the domain sites sit under; emptying it falls back to `<deployment>.convex.site/sites/<slug>`.
- **An address is a plan entitlement.** `publicAddress` is false on Free and true on every paid plan. Free is for planning and building a site; `sites.setSlug` and `sites.publish` both refuse without it, so a free account cannot reach an address by a route the client happens not to offer. The plan card names the entitlement, and the globe sells it.
- Publishing: `sites.publish` pins the current version; `convex/http.ts` serves it by Host — a site's own address, or a custom domain pointed at it — and still at `/sites/<slug>`, with a content-security-policy that allows markup, inline styles and Google Fonts only. `sites.currentHtml` backs the preview.
- `plans.ts` is the catalog, modelled on Wegic's plans and credits (help.wegic.ai "Plan and Credits", wegic.ai/pricing): **Free** with 20 welcome credits, 10 a month after that and one site; **Starter** at $39.90/month or $286.80/year with 600 credits a month, 15 sites and no custom domain or extra credits; **Premium** at $69.90/month or $502.80/year with 2000 credits a month, unlimited sites, a custom domain and extra credits. A site build holds 40 credits, Wegic's published figure (600 ÷ 40 is its 15 sites a month); the chat, edit, image and video costs and the top-up pack prices are Forge's own until Wegic publishes theirs. A conversational reply costs 1 credit — not nothing, since it is still a provider call, but a fortieth of a build. Free's allowance buys conversation rather than builds: its welcome grant and its monthly allowance together open at less than a build costs, so a free member can plan a site indefinitely and still has to upgrade to build one. A plan may be unlimited (`monthlyCredits: null`), in which case no request is held against a balance and its spends are only written to the ledger — but no plan in the catalog is, and a test holds it that way: an unlimited plan is unmetered provider spend against a fixed monthly price. Premium's sites and visitors are uncapped; its model calls are not. The catalog is product configuration rather than user data, served to the client by `billing.catalog` so nothing in `docs/` carries a price.
- Spending is reserve → run → settle. `billing.reserve` holds a request's credits in one transaction (so a burst of requests cannot overspend), `billing.settle` turns the hold into a spend for what the request actually cost (never more than the hold), and `billing.release` gives it back after a failure. These are internal mutations for the generation pipeline; a client can only read its balance.
- Payments go through Stripe, over its REST API from `convex/stripe.ts` (no SDK). `billing.checkout` opens a Checkout Session for a plan (a subscription, monthly or yearly) or a credit pack (a one-off payment) with the member's id in the session metadata; `billing.portal` opens Stripe's billing portal; `billing.cancel`/`resume` set `cancel_at_period_end` on the Stripe subscription as well as locally. Stripe posts to `https://<deployment>.convex.site/stripe/webhook`, where the signature is verified with `STRIPE_WEBHOOK_SECRET` and each event id is recorded in `stripeEvents` before it is applied, so a redelivery can never grant twice. Handled events: `checkout.session.completed` (plan or pack), `customer.subscription.updated` (cancellation, period, and a plan change made through the portal), `customer.subscription.deleted` (back to Free), and `invoice.paid` with `billing_reason=subscription_cycle` (a renewal: the leftover expires and the allowance is granted again). Until the keys are set, checkout says payments are not open; an account can still be put on a plan or given credits from the Convex dashboard with the internal mutations `billing.grantPlan` (`{ email, plan: "starter" }`) and `billing.grantTopUp` (`{ email, pack: "topup-100" }` or `{ email, credits: 25 }`).
- `admins.ts` is who runs the deployment. It is configuration, like the plan catalog: `ADMIN_EMAILS` (or the default in the file) names the accounts that `ensureCurrent` holds on the top plan, so the people testing the product are never stopped by a plan gate or a balance. Nothing a client can call reads or changes it.
- `settings` stores the Appearance choices per user. The device keeps a `forge-settings` copy in `localStorage` to paint before Convex answers, and a signed-in account's saved values replace it.
- Sign-in goes through `auth.signIn`, a thin wrapper around Convex Auth's own action: a guest's data moves to the account they sign in to, and a member's free subscription is created on their first sign-in.
- `users.deleteAccount` removes everything the account owns, its auth accounts and sessions, and the user row; the client then signs out and starts a fresh guest session.
- Coming back from a provider is its own state. A sign-in that leaves the page (Google, Apple, or a magic link opened later) finishes on the return leg, so the client tracks it: `auth.handoff()` reports the provider while the exchange is in flight and the reason if it fails, and the gate shows "Signing you in…" rather than the front door that started it. A failed exchange says why instead of returning an untouched sign-in screen. The app also names its own return address (`location.origin + location.pathname`) rather than sending `redirectTo: "/"` for the deployment to resolve, so a `SITE_URL` missing the app's path cannot land the browser on a page that is not the app. Because an OAuth verifier has to survive the trip out and back, storage falls back to `sessionStorage` before memory.
- The dashboard opens on the server's answer, and asks for one directly. The live `users.me` subscription only answers once the WebSocket has re-authenticated, so a member who had just signed in could sit behind the gate holding valid tokens with the single-use code already stripped from the URL. On a landed sign-in the client now also asks `users.me` over HTTP with the fresh token and unlocks on that; a `null` from the live query while its socket reconnects no longer counts as "you are a guest". An anonymous row still locks, so nothing but the server can reveal the app.
- Deploying is a separate step from the Pages deploy: pushing to `main` publishes `docs/`, but new tables and functions only exist once someone with the deploy key runs `npx convex deploy`. A client calling a function the deployment does not have yet fails with `Could not find public function for '<module>:<name>'`. The `connections`, `workspaces` and `apps` tables from the previous direction are gone from the schema; if the deployment still holds rows in them, clear those tables in the dashboard before the push.
- The browser talks to whichever deployment `<meta name="convex-url">` in `docs/index.html` names. Change that meta to point a build at production.
- `src/` is the vanilla-JS client: `data.js` owns the session lifecycle (guest sign-in, token refresh, magic-link and OAuth code exchange, sign-out) and exposes `sites`, `messages`, `domains`, `billing`, `settings` and `account`; `browser.js` wires it to the real Convex clients. `npm run build` bundles it to `docs/forge-data.js`, which `docs/app.js` reads as the `ForgeData` global.
- `npm test` runs the Convex functions in-memory with convex-test plus the session lifecycle tests; `npm run typecheck` checks `convex/`. `node scripts/smoke-convex.mjs <deployment url>` exercises a live deployment end to end over HTTP.

### Deployment environment variables

Set with `npx convex env set NAME value` against the target deployment.

| Variable | Purpose |
|---|---|
| `SITE_URL` | Where sign-in links and OAuth callbacks return to, e.g. `https://xgamer791.github.io/forge-nexxus` |
| `ADMIN_EMAILS` | Comma-separated addresses that run the deployment. An admin account is held on the top plan — every path that touches a subscription puts it back, so a period ending or a Stripe downgrade cannot strand it — and never spends its own money to test what a member gets. Unset falls back to the list in `convex/admins.ts`; set it empty for a deployment with no admins. |
| `SITES_DOMAIN` | The domain published sites sit under, e.g. `sites.forgenexxus.com` (the default). Its wildcard `*.sites.forgenexxus.com`, and every custom domain, must be pointed at this deployment and added to it as a custom domain. Setting it empty serves sites at `<deployment>.convex.site/sites/<slug>` instead. |
| `JWT_PRIVATE_KEY`, `JWKS` | Session token signing keys (RS256 pair) |
| `AUTH_RESEND_KEY` | Resend API key for magic-link email; `AUTH_EMAIL_FROM` overrides the sender once a domain is verified |
| `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET` | Google OAuth client. Authorized redirect URI: `https://<deployment>.convex.site/api/auth/callback/google` |
| `AUTH_APPLE_ID`, `AUTH_APPLE_SECRET` | Sign in with Apple Services ID and client secret. Return URL: `https://<deployment>.convex.site/api/auth/callback/apple` |
| `AI_BASE_URL`, `AI_API_KEY`, `AI_MODEL` | The chat completions endpoint that builds sites: any OpenAI-compatible base URL (e.g. `https://api.openai.com/v1`, `https://api.anthropic.com/v1`, `https://api.z.ai/api/paas/v4`, an OpenRouter or Gemini compatibility URL), its key, and the model name. `AI_MAX_TOKENS` (default 10000) caps the reply. |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | The Stripe secret key, and the signing secret of the webhook endpoint pointed at `https://<deployment>.convex.site/stripe/webhook` (events: `checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.paid`). |
| `STRIPE_PRICE_STARTER_MONTH`, `STRIPE_PRICE_STARTER_YEAR`, `STRIPE_PRICE_PREMIUM_MONTH`, `STRIPE_PRICE_PREMIUM_YEAR` | Recurring Stripe price ids for each plan and interval. A plan without a price id cannot be bought. |
| `STRIPE_PRICE_TOPUP_100`, `STRIPE_PRICE_TOPUP_300`, `STRIPE_PRICE_TOPUP_1000` | One-off Stripe price ids for the credit packs in `convex/plans.ts`. |

Apple's client secret is a JWT that expires within six months; generate it with `node scripts/apple-client-secret.mjs --team TEAMID --key KEYID --client SERVICES_ID --p8 ./AuthKey_KEYID.p8` and set the new value before the old one lapses.

## Layout requirements

The prompt docks to the browser viewport with a 20px bottom gap. Bottom sheets meet the viewport edge and the navigation drawer spans its height. These must remain independent of the app container height. iOS safe-area top padding and native system fonts are retained; the operating-system status bar and Dynamic Island are not drawn by the app. The build thread scrolls in the space between the top bar and the prompt and replaces the greeting once a site has messages. The account sheet opens from the drawer footer.

## Review

Test normal production layout separately: with a 932px viewport and a deliberately shortened 873px container, the prompt bottom must remain 912px and bottom sheets must end at 932px.
