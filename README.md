# Forge Nexxus

A mobile website builder backed by Convex. A member describes the site they want in the composer, Forge builds it as a site in pages — one shell every page shares, and a page at its own address for each part of the site — and each follow-up prompt edits it. The build thread is where that conversation lives, the drawer lists their sites, and a site can be previewed and published to a public address. Everything runs on monthly credits: a plan grants an allowance per period, top-ups add more where the plan allows, and nothing rolls over. Users never see AI spend — only their credits — because the model is called server-side with the deployment's own key.

Live app: https://xgamer791.github.io/forge-nexxus/

`CLAUDE.md` holds the standing rules for working on this repository, the first being that all user data lives in Convex.

## Hosting

Standard GitHub Pages only, using the existing `.github/workflows/pages.yml` workflow and `docs/` output. Keep all asset paths relative to support `/forge-nexxus/`. `docs/forge-data.js` is a built artifact (see below) and is committed so Pages needs no build step.

## Local preview

Run `npm run dev`, then open http://localhost:4173/forge-nexxus/ . Any static server can also serve `docs/` directly. Rebuilding the data bundle or running the tests needs `npm install` first.

## What is in the app

- **Sign-in gate** (`docs/auth.js`): guests never reach the app. Building needs an account so credits belong to someone; a magic link, Google or Apple all create one.
- **Globe (top right)**: the active site's address, in a panel that comes down from the top — it belongs to the button that opened it, not to the thumb, so it keeps every sheet part and turns the geometry over: square at the top edge, rounded below, handle at the bottom. The name under the hosting domain is editable there, with the live link and whether it is published, and a custom domain is added, checked and removed in the same sheet on the plans that include them. Changing the address warns first, naming the address that stops answering. On a plan without `publicAddress` the globe opens the upsell instead of the picker — what an address and a custom domain come with, and the way through to the plan screen.
- **Drawer**: New site, the account's sites (most recently edited first, with rename and delete), a credits card showing the plan, what is left of this period and when it resets, and the account footer.
- **Settings**: Profile (name, linked sign-in methods, sign out, delete account), Appearance, Memory (what Forge remembers about you across sites, with a switch and Forget), Plan & credits (current plan and meter, plan cards with monthly and yearly prices, top-up packs where the plan allows them, Manage billing, downgrade at period end), Usage (the credit ledger), and Domains (custom hostnames pointed at a site, Pro and Ultra).
- **Composer**: the first prompt creates a site named after it and builds the first version; later prompts edit it. The reply appears in the thread as "Building your site…" until the build lands, and as a failure (with the reason) if it does not. A guest who somehow reaches it is sent to sign in.
- **Site bar and preview**: the bar above the composer names the active site and its state. Every Preview control opens the latest build in an unrestricted frame inside the app, so its scripts, forms and same-origin browser APIs run there just as they do on the published site: the whole screen on a phone, and on a computer a chosen device or a website's width. A site built in pages has a strip of its pages along the bottom of the frame, and the site's own links work inside it: an in-page link stays on its page, and a link to another page opens that page at the site's address while the build on show is the live one — the strip then marks no page until one is chosen from it. Download code and Unpublish / Publish sit in the drawer's site menu. Sites on a plan without `removeBadge` carry a small "Built with Forge" badge, added as the page is served rather than stored, so upgrading takes it off every build at once. Publish is disabled on a plan without `publicAddress`, and says why, because there is nowhere to publish to.

## Both surfaces

`docs/` is one app: the same page serves the phone and the desktop website, so
a feature is never on one and missing from the other. Width is what differs.
`--shell` is the content column — 640px, 860px from 900px up — and the
composer, sheets, drawer and overlays are all positioned from it. The desktop
layer is a single `@media(min-width:900px)` block at the end of
`docs/styles.css`: the column widens, bottom sheets become centred dialogs, the
domain panel becomes a card under the globe, the drawer docks to the window as
a sidebar, and the preview opens at a website's width. `@media(hover:hover)`
adds the pointer affordances. Both widths get checked before a change is done;
`CLAUDE.md` holds that as a standing rule.

## Convex

- `convex/` holds the schema, Convex Auth setup (`auth.ts`), and the site, conversation, message, domain, billing, user, settings, and memory functions. `npx convex dev` pushes them to the deployment named in `.env.local` (`CONVEX_DEPLOYMENT` plus `CONVEX_DEPLOY_KEY`, never committed) and regenerates `convex/_generated/`.
- `sites` is what a user builds. Each site owns a conversation (its build thread); `sites.create` makes both, `sites.remove` deletes the thread, its messages and the site's domains, and `messages.send` bumps the site's `updatedAt` so the drawer orders by last edit. Only members create sites, and a plan caps how many an account holds.
- `domains` are hostnames pointed at a site, added the way Wegic asks for them: one record. `domains.add` normalises a pasted URL to its host, refuses duplicates, anything already held by another account and anything under the hosting domain, and needs a plan with `customDomains`. `domains.list` carries the record to add — a `CNAME` for a subdomain, the registrar's root `ALIAS` for a bare domain — pointing at the site's own address. `domains.verify` is one button: the server resolves the hostname over DNS-over-HTTPS and writes back `active`, or stays `pending` with what it actually saw, so a browser can never mark its own domain verified. A domain that already resolves here is served while verification catches up.
- `subscriptions` is one row per member: the plan, the period, `credits` left this period, `reserved` by requests still running, and `granted` (the period's allowance plus its top-ups, which is the meter's full mark). Periods are one calendar month; when one ends the leftover expires, a scheduled downgrade lands, and the new allowance is granted. `creditLedger` records every movement and `creditHolds` tracks in-flight requests.
- `generate.run` answers a prompt. It records the prompt and a pending reply, holds the credits for the request (`generate` for a first build, `edit` after), sends the system prompt, the current page and the recent thread to any OpenAI-compatible chat completions endpoint, and stores the returned page as a `siteVersions` row before settling the hold. The model chooses between two replies: a build, which is one sentence and the complete page in an `html` fence, or an answer in plain prose when the user asked a question rather than for a change. An answer stores no version, leaves the current page alone, and settles the build hold at the `chat` rate, so asking what would suit the site costs a credit rather than a rebuild. A reply that starts a page and does not finish one is a failure, not an answer. A balance too thin for a build does not refuse the message: the turn becomes talk-only, held at the chat rate, with the model told it may not build and what standing in the way costs, so a free member can plan a site before paying for one. A page returned on such a turn is dropped rather than handed over for a credit. A failed call marks the reply `failed` with a scrubbed reason and releases the hold, so a build that produced nothing costs nothing. Routing is the deployment's to choose: conversation goes to whatever `AI_BASE_URL`, `AI_API_KEY` and `AI_MODEL` name. Planning and building go to `AI_BUILD_BASE_URL`, `AI_BUILD_API_KEY` and `AI_BUILD_MODEL` when those are set, and otherwise to the chat route. Both speak the OpenAI chat shape (`chatRoute` in `convex/generate.ts`), and every picture goes to the image model in `AI_IMAGE_API_KEY` and `AI_IMAGE_MODEL` (`convex/images.ts`); the two routes are independent and never share a model, and `npx convex run generate:routing` reports which host and model each path resolves to without showing a key. A page asks for a picture with `<img src="forge-image:N" data-forge-image="…">`; before the version is stored each one is made as its own `image` request (held, settled on success, released on failure), saved to Convex storage, recorded in `siteImages`, and swapped in, and one that cannot be made becomes a quiet placeholder so a page never points at nothing. Until `AI_API_KEY` is set the build is refused with "Site generation isn.t set up on this deployment yet".
- **Design research and continuity.** A first build researches businesses in Los Angeles, New York, San Diego and Miami through a separate Playwright worker and chooses a reference site. Its page discovery agent reads the reference's header and navigation and chooses the pages the site will have -- the home page first, five at most, never a legal, account, cart or search page. SkillUI Ultra (`skillui --mode ultra --screens 5 --format both`) then extracts the reference's design: tokens, type, spacing, components, layout, interactions and screenshots, packaged as a `.skill`. The package is saved per site and read on every later edit; a rebuild extracts the same address again, and deletion discards it. Every first build and rebuild is written a page at a time by a crew: a builder and an auditor for the header, two of each for the body, one of each for the footer. Each auditor checks its part against the extract the moment it is written, and a page is kept only once all four agree. Each step checkpoints what its crew wrote, as page-at-a-time builds always have: a part the step's clock stops while it is being written is saved and carried on from that character in the next step. Thread edits are checked by the same auditors before they save. Builders write original copy and ask for new images through Nano Banana Lite; `designgod.ts` controls fonts and typography. `buildEvents` records each search, the chosen pages, the SkillUI run, every builder and every auditor verdict, and the progress UI reads those events. Research fails closed if the worker is missing or SkillUI Ultra returns no package, and a part its auditor never agrees to stops the build with its credits returned.
- Addresses: every site answers on `<slug>.<SITES_DOMAIN>` once that domain is set up, and at `<deployment>.convex.site/sites/<slug>` until then — see [`HOSTING.md`](HOSTING.md). **A site's first address is assigned by Forge, never picked.** `assignSlug` in `convex/sites.ts` makes it when a build finishes (or when a site with none is published by hand): the business name from the website questions is a soft seed and is used when it makes a real address (`bakery-on-main`); when it is missing, too short, reserved or generic (`site`, `my-site`, `website`…) the address is two plain words and a short tail instead (`amber-anvil-k3x9`). A collision adds a `-xxxx` tail, and nothing passes 40 characters. No screen asks for an address to get online, and `sites.setSlug` refuses a site that has none yet. What is the member's is the one change afterwards: `sites.setSlug` takes it (letters, numbers and hyphens, 3–40 characters, reserved labels refused) from the globe, while `sites.slugAvailable` answers the field as it is typed. The address is kept through unpublishing so links keep working. `SITES_DOMAIN` names the domain sites sit under; emptying it falls back to `<deployment>.convex.site/sites/<slug>`.
- **An address is a plan entitlement.** `publicAddress` is true on every plan in the catalog. An unpaid account (a member who has not checked out, or whose paid period has ended) cannot publish; `sites.setSlug` and `sites.publish` both refuse without it. The plan card names the entitlement, and the globe sells it.
- **A finished build publishes itself.** `generate.finish` saves the version and, in the same transaction, `sites.publishBuild` puts it on the site's Forge address — for a first build and for every edit after it — so a built site always has a link and that link always serves the latest build. A site that has no address is assigned one there, without asking and without waiting on anyone; one it already has — assigned earlier, or changed since — is kept. Two things do not change: a plan without `publicAddress` gets no address (the globe is still where joining a plan is offered), and a site its owner unpublished stays offline until they publish it again. The only host is the one `SITES_DOMAIN` names, or this deployment's own origin while it names none. The first build's reply in the thread ends with the address.
- Publishing: `sites.publish` pins the current version by hand (putting an offline site back); `convex/http.ts` serves it by Host — a site's own address, or a custom domain pointed at it — and still at `/sites/<slug>`. No content-security-policy is sent, by the owner's decision, so a published page runs its scripts, loads from any host and submits its forms. `sites.currentHtml` backs the preview.
- `plans.ts` is the catalog, modelled on Wegic's plans and credits (help.wegic.ai "Plan and Credits", wegic.ai/pricing): **Starter** at $60/month or $432/year with 2500 credits a month, 15 sites and no custom domain or extra credits; **Pro** at $100/month or $720/year with 5000 credits a month, unlimited sites, a custom domain and extra credits; **Ultra** at $200/month or $1,440/year with 12000 credits a month and every Pro entitlement. There is no Free plan. Unused credits do not roll over: each period resets to the plan's allowance. Rows and Stripe metadata that still say `premium` are read as Pro. A site build holds 40 credits, Wegic's published figure (600 ÷ 40 is its 15 sites a month); the chat, edit, image and video costs and the top-up pack prices are Forge's own until Wegic publishes theirs. A conversational reply costs 1 credit — not nothing, since it is still a provider call, but a fortieth of a build. A member who has not checked out, or whose paid period has ended, is unpaid: they can talk, they cannot build, and they are not shown as a product tier. A plan may be unlimited (`monthlyCredits: null`), in which case no request is held against a balance and its spends are only written to the ledger — but no plan in the catalog is, and a test holds it that way: an unlimited plan is unmetered provider spend against a fixed monthly price. Pro and Ultra sites and visitors are uncapped; their model calls are not. The catalog is product configuration rather than user data, served to the client by `billing.catalog` so nothing in `docs/` carries a price.
- Spending is reserve → run → settle. `billing.reserve` holds a request's credits in one transaction (so a burst of requests cannot overspend), `billing.settle` turns the hold into a spend for what the request actually cost (never more than the hold), and `billing.release` gives it back after a failure. These are internal mutations for the generation pipeline; a client can only read its balance.
- Payments go through Stripe, over its REST API from `convex/stripe.ts` (no SDK). `billing.checkout` opens a Checkout Session for a plan (a subscription, monthly or yearly) or a credit pack (a one-off payment) with the member's id in the session metadata; `billing.portal` opens Stripe's billing portal; `billing.cancel`/`resume` set `cancel_at_period_end` on the Stripe subscription as well as locally. Stripe posts to `https://<deployment>.convex.site/stripe/webhook`, where the signature is verified with `STRIPE_WEBHOOK_SECRET` and each event id is recorded in `stripeEvents` before it is applied, so a redelivery can never grant twice. Handled events: `checkout.session.completed` (plan or pack), `customer.subscription.updated` (cancellation, period, and a plan change made through the portal), `customer.subscription.deleted` (back to unpaid), and `invoice.paid` with `billing_reason=subscription_cycle` (a renewal: the leftover expires and the allowance is granted again). Until the keys are set, checkout says payments are not open; an account can still be put on a plan or given credits from the Convex dashboard with the internal mutations `billing.grantPlan` (`{ email, plan: "starter" }`) and `billing.grantTopUp` (`{ email, pack: "topup-1000" }` or `{ email, credits: 25 }`).
- `admins.ts` is who runs the deployment. It is configuration, like the plan catalog: `ADMIN_EMAILS` (or the default in the file) names the accounts that `ensureCurrent` holds on the top plan, so the people testing the product are never stopped by a plan gate or a balance. Nothing a client can call reads or changes it.
- `settings` stores the Appearance choices per user. The device keeps a `forge-settings` copy in `localStorage` to paint before Convex answers, and a signed-in account's saved values replace it.
- `memories` is what Forge remembers about a member between conversations. After each answered turn, `memory.reflect` asks the chat model — with only the exchange and the numbered list it already holds, never the page — for JSON naming what to add, replace or forget, and the server applies it under a cap. Every text turn carries the list as one system message framed as untrusted content; image calls never see it. `settings.memory` switches reading and writing off without deleting anything; Settings → Memory lists it and forgets it, one row or all.
- Sign-in goes through `auth.signIn`, a thin wrapper around Convex Auth's own action: a guest's data moves to the account they sign in to, and a member's unpaid subscription is created on their first sign-in.
- `users.deleteAccount` removes everything the account owns, its auth accounts and sessions, and the user row; the client then signs out and starts a fresh guest session.
- Coming back from a provider is its own state. A sign-in that leaves the page (Google, Apple, or a magic link opened later) finishes on the return leg, so the client tracks it: `auth.handoff()` reports the provider while the exchange is in flight and the reason if it fails, and the gate shows "Signing you in…" rather than the front door that started it. A failed exchange says why instead of returning an untouched sign-in screen. The app also names its own return address (`location.origin + location.pathname`) rather than sending `redirectTo: "/"` for the deployment to resolve, so a `SITE_URL` missing the app's path cannot land the browser on a page that is not the app. Because an OAuth verifier has to survive the trip out and back, storage falls back to `sessionStorage` before memory.
- The dashboard opens on the server's answer, and asks for one directly. The live `users.me` subscription only answers once the WebSocket has re-authenticated, so a member who had just signed in could sit behind the gate holding valid tokens with the single-use code already stripped from the URL. On a landed sign-in the client now also asks `users.me` over HTTP with the fresh token and unlocks on that; a `null` from the live query while its socket reconnects no longer counts as "you are a guest". An anonymous row still locks, so nothing but the server can reveal the app.
- Deploying is a separate step from the Pages deploy: pushing to `main` publishes `docs/`, but new tables and functions only exist once someone with the deploy key runs `npx convex deploy`. A client calling a function the deployment does not have yet fails with `Could not find public function for '<module>:<name>'`. The `connections`, `workspaces` and `apps` tables from the previous direction are gone from the schema; if the deployment still holds rows in them, clear those tables in the dashboard before the push.
- The browser talks to whichever deployment `<meta name="convex-url">` in `docs/index.html` names. Change that meta to point a build at production.
- `src/` is the vanilla-JS client: `data.js` owns the session lifecycle (guest sign-in, token refresh, magic-link and OAuth code exchange, sign-out) and exposes `sites`, `messages`, `domains`, `billing`, `settings`, `memory` and `account`; `browser.js` wires it to the real Convex clients. `npm run build` bundles it to `docs/forge-data.js`, which `docs/app.js` reads as the `ForgeData` global.
- `npx convex run generate:routing` names the model each kind of work goes to, the design auditors included; `npx convex run probe:chat` calls the chat route once and reports what it answers with (status, reply fields, content vs reasoning characters, `finish_reason`, the provider's error). Neither returns a key. Together they separate a rejected key, a slow model, and a reasoning model that returns only its thinking.
- `npm test` runs the Convex functions in-memory with convex-test plus the session lifecycle tests; `npm run typecheck` checks `convex/`. `node scripts/smoke-convex.mjs <deployment url>` exercises a live deployment end to end over HTTP.

### Deployment environment variables

Set with `npx convex env set NAME value` against the target deployment.

| Variable | Purpose |
|---|---|
| `SITE_URL` | Where sign-in links and OAuth callbacks return to, e.g. `https://xgamer791.github.io/forge-nexxus` |
| `ADMIN_EMAILS` | Comma-separated addresses that run the deployment. An admin account is held on the top plan — every path that touches a subscription puts it back, so a period ending or a Stripe downgrade cannot strand it — and never spends its own money to test what a member gets. Unset falls back to the list in `convex/admins.ts`; set it empty for a deployment with no admins. |
| `SITES_DOMAIN` | The domain published sites sit under, e.g. `sites.forgenexxus.com`. **Unset by default, and it must stay unset until that domain actually answers** — sites are then served at `<deployment>.convex.site/sites/<slug>`, which needs no DNS. Setting it makes every site's address `<slug>.<SITES_DOMAIN>`, so a deployment whose wildcard is not resolving and serving yet hands out links that cannot open. Branded addresses are served by a small router on the Cloudways box rather than by Convex, so no Convex Pro plan is involved: **[`HOSTING.md`](HOSTING.md) is the runbook and [`cloudways/sites-router/`](cloudways/sites-router/README.md) is what gets installed**. `node scripts/check-sites-hosting.mjs --domain <domain>` says whether it is ready. |
| `JWT_PRIVATE_KEY`, `JWKS` | Session token signing keys (RS256 pair) |
| `AUTH_RESEND_KEY` | Resend API key for magic-link email; `AUTH_EMAIL_FROM` overrides the sender once a domain is verified |
| `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET` | Google OAuth client. Authorized redirect URI: `https://<deployment>.convex.site/api/auth/callback/google` |
| `AUTH_APPLE_ID`, `AUTH_APPLE_SECRET` | Sign in with Apple Services ID and client secret. Return URL: `https://<deployment>.convex.site/api/auth/callback/apple` |
| `AI_BASE_URL`, `AI_API_KEY`, `AI_MODEL` | **Conversation and site building: any provider that speaks the OpenAI chat-completions shape.** Unset, these fall back to `https://api.deepseek.com/v1` and `deepseek-flash` — DeepSeek v4.1 Flash, which is what this deployment runs — so a missing variable lands on the working route rather than nowhere. Any other OpenAI-shaped provider works by naming it here. Nothing is refused before it is tried: whatever these name is what gets called, and a provider that cannot serve it answers in its own words, which is what the thread and the failed screen show (`convex/generate.ts`, `chatRoute`). Two things are worth knowing when one fails. Google's *native* `/v1beta` endpoint does not speak this shape, so `/chat/completions` 404s there — use `https://generativelanguage.googleapis.com/v1beta/openai` if you point chat at Gemini. And an image model cannot write HTML, so it belongs in `AI_IMAGE_MODEL` rather than here. `AI_BUILD_MODEL`, `AI_BUILD_BASE_URL` and `AI_BUILD_API_KEY` send planning and the build to their own provider. Chat stays on `AI_MODEL`. Unset, planning and a build fall back to the chat route. On `glm-5.3`, planning asks for `max` and the build asks for `high`. `npx convex run generate:routing` reports chat, planning and the build. `AI_REASONING_EFFORT` sets how hard a build thinks. The levels a route accepts are the provider's. DeepSeek documents three efforts — low, high, max — under seven names it maps itself (`minimal` and `low` → low; `medium`, `high` and `xhigh` → high; `max` and `ultra` → max), and all seven are passed through as written. Gemini takes `low`, `medium` and `high`, and a name it lacks meets the nearest it has. Unset, DeepSeek asks for `max` on a build and on the strategist's brief, `high` on a reply and the memory note, and Gemini for `high` throughout. The field rides only the routes measured to read it — `EFFORT_MODELS` in `convex/generate.ts` — so a provider nobody has tried still gets a plain body, and `generate:routing` reports what each route will send. The field rides a request only where it has been measured to work — a Gemini chat host, or one of the models named in `EFFORT_MODELS` in `convex/generate.ts` — so a provider nobody has tried still gets a plain body. On those models it is a build's alone: a chat turn, the strategist and the memory note stay plain, since none of them is worth a long deliberation. `generate:routing` reports the effort each route will send. `AI_MAX_TOKENS` caps one reply; unset, a build gets 96000 and a conversation 32000, and `npx convex run generate:routing` reports which. That ceiling covers the model's thinking as well as its answer: a reasoning model bills what it thought inside the same budget, so a ceiling that only fits the page comes back as thinking and no page at all. Set this below what a whole site needs and that is what a build does. A provider with a lower cap is asked again inside it, a reply that was all thinking is asked again inside a wider one, and a page cut off at the cap is continued rather than failed. `AI_MODEL_LABEL` overrides what the agent calls its model; unset, the pretty name is used only for the exact default id, and any other model reports its own id. |
| `AI_IMAGE_API_KEY`, `AI_IMAGE_MODEL` | **Every picture: Gemini Nano Banana 2 Lite, and nothing else** (`convex/images.ts`). `AI_IMAGE_MODEL=gemini-3.1-flash-lite-image` (the default when unset) and the Gemini key. Any model that is not a `flash-lite-image` build is ignored in favour of Lite unless `AI_IMAGE_MODEL_OVERRIDE=true` is also set, so full Nano Banana 2 is a decision, not a typo. `AI_IMAGE_BASE_URL` defaults to `https://generativelanguage.googleapis.com/v1beta`. Without the key, builds still finish: the agent is told to draw with CSS and SVG instead. |
| `DESIGN_WORKER_URL`, `DESIGN_WORKER_TOKEN` | HTTPS origin and shared bearer token of the design worker (Playwright, the page discovery agent and SkillUI Ultra); required for first builds and rebuilds. The worker also needs `BRAVE_SEARCH_API_KEY`, plus `AI_RESEARCH_API_KEY` (Gemini; falls back to `GEMINI_API_KEY`, then `AI_IMAGE_API_KEY`), `AI_RESEARCH_MODEL` (default `gemini-3.8-flash`) and `AI_RESEARCH_BASE_URL` (default Gemini's `v1beta`). The chooser screenshots each shortlisted homepage and accepts it with Gemini 3.8 Flash at thinking level `high` before that URL is chosen. See `design-worker/README.md`. The old Awwwards reviewer is retired. |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | The Stripe secret key, and the signing secret of the webhook endpoint pointed at `https://<deployment>.convex.site/stripe/webhook` (events: `checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.paid`). |
| `STRIPE_PRICE_STARTER_MONTH`, `STRIPE_PRICE_STARTER_YEAR`, `STRIPE_PRICE_PRO_MONTH`, `STRIPE_PRICE_PRO_YEAR`, `STRIPE_PRICE_ULTRA_MONTH`, `STRIPE_PRICE_ULTRA_YEAR` | Recurring Stripe price ids for each plan and interval. A plan without a price id cannot be bought. `STRIPE_PRICE_PREMIUM_MONTH` / `STRIPE_PRICE_PREMIUM_YEAR` still map to Pro so existing subscriptions keep working. |
| `STRIPE_PRICE_TOPUP_1000`, `STRIPE_PRICE_TOPUP_2000`, `STRIPE_PRICE_TOPUP_3000`, `STRIPE_PRICE_TOPUP_4000`, `STRIPE_PRICE_TOPUP_5000`, `STRIPE_PRICE_TOPUP_10000` | One-off Stripe price ids for the credit packs in `convex/plans.ts`. |

## Layout requirements

The prompt docks to the browser viewport with a 20px bottom gap. Bottom sheets meet the viewport edge and the navigation drawer spans its height. These must remain independent of the app container height. iOS safe-area top padding and native system fonts are retained; the operating-system status bar and Dynamic Island are not drawn by the app. The build thread scrolls in the space between the top bar and the prompt and replaces the greeting once a site has messages. The account sheet opens from the drawer footer.

## Review

`?reference` provides a 430 × 932 logical reference frame. `&screen=attachments`, `account`, `navigation`, `settings`, `appearance`, `profile`, `plan`, `usage`, `domains`, or `preview` exposes each menu for comparison. `&theme=light` or `&theme=dark` sets the Appearance theme. Test normal production layout separately: with a 932px viewport and a deliberately shortened 873px container, the prompt bottom must remain 912px and bottom sheets must end at 932px. Native iOS browser behavior still requires device verification.
